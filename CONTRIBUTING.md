# Contributing to MCPBlueprint

Thanks for your interest in contributing. This project grows through community input - new agent patterns, better definitions, improved templates, and real-world examples all make it more useful for everyone.

---

## What You Can Contribute

- **New agent type definitions** - if you've identified a pattern not covered by the existing 9
- **Improvements to existing definitions** - clearer explanations, better examples, corrected details
- **New templates** - starter configs for platform types not yet covered
- **New examples** - real-world reference architectures (keep them generic, no proprietary details)
- **Risk scanner rules** - additional rules for the scanner's rule set
- **Bug fixes** - broken links, incorrect config examples, outdated instructions

---

## Getting Started

```bash
git clone https://github.com/<org>/<repo>.git
cd <repo>
npm install
```

> **Note:** Update the clone URL above if this repo is moved or renamed.

Most contributions are markdown - no build step required. For changes to `lib/` or `agents/*/agent.js`, test your changes locally before opening a PR:

```bash
node --experimental-vm-modules <your-file>
```

See [docs/getting-started.md](docs/getting-started.md) for the full local setup sequence, including generating `config/platform.json` and running the risk scanner.

## Meet Matt the Maintainer

**Matt the Maintainer** is the bot that triages issues, reviews PRs, and keeps things moving in this repo. When you open an issue or PR, Matt will respond - acknowledging your contribution, asking clarifying questions, or flagging next steps. Matt is automated, but the responses are grounded in the project's actual guidelines, not generic boilerplate.

If Matt flags something on your PR, address it and re-request review. If you think Matt got it wrong, leave a comment explaining your reasoning - a human maintainer will step in.

## Who to Work With

**For documentation, definitions, templates, and examples:**
Open a pull request directly. If you're unsure whether your addition fits the project scope, open an issue first and tag it `question`.

**For changes to `lib/` (agent-bus, agent-registry, correlation):**
These modules are shared across all agents - a change here affects everything. Open an issue before you write any code, describe what you're changing and why, and wait for a maintainer to sign off on the approach. Tag the issue `lib-change`.

**For new agent types:**
Open an issue tagged `new-agent` before building. Describe the pattern, what problem it solves, and why the existing 9 don't cover it. Maintainers will confirm fit before you invest time in the full folder.

**For changes to an existing agent type:**
Some agent types have designated maintainers. Open an issue tagged `agent-maintainer` and describe your proposed change - the right person will be looped in.

**For large or breaking changes:**
Post in the issue tracker first. Tag it `discussion`. Don't open a PR for a large change without a prior issue - it's harder to redirect work that's already done.

**To signal you're working on something:**
Comment on the open issue with "I'm working on this" so two people don't build the same thing. Maintainers will acknowledge.

## How to Submit a PR

1. Fork the repo
2. Create a branch named for your change: `add-streaming-agent-pattern` or `fix-guardrail-config-example`
3. Make your changes
4. Open a pull request with:
   - A clear title (what changed, not why)
   - A description explaining why the change is needed and what you decided
   - A link to the related issue if one exists (`Closes #123`)
5. A maintainer will review and respond

Keep PRs focused - one change per PR. If you're fixing a bug and improving something adjacent, do them separately.

## What's Automatically Maintained

The following are managed automatically and shouldn't be edited by hand:

- **`config/platform.json`** - generated by the onboarding script (`admin-panel/onboarding.js`). Edit the prompts or script, not the output file.
- **`risk-scanner/output/risk-profile.json`** - generated by `risk-scanner/scanner.js`. Re-run the scanner to update it; don't patch the output directly.
- **Dependency updates** - handled via automated PRs. Review and merge; don't manually update `package.json` versions unless fixing a specific vulnerability.

If you see one of these files in a PR, it should have been regenerated by its source - not hand-edited.

## Agent Definition Standards

If you're adding a new agent type, your folder must include:

- `definition.md` - what the agent does, when to use it, when not to use it
- `config.example.json` - a working example configuration with comments
- `test.md` - how to verify the agent is working correctly

Follow the format of existing agent folders for consistency.

---

## What We Won't Merge

- Definitions that reference specific proprietary platforms or services by name
- Integrations built into the core framework (suggest patterns, don't wire things up)
- Anything that removes the modular opt-in nature of the system
- Config examples with hardcoded credentials or real API keys
